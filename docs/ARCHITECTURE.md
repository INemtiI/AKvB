# Архитектура

## Уровни системы

Система построена как классический сетевой стек из трёх уровней. Каждый уровень ничего не знает о внутренностях соседей и общается через простые интерфейсы (байты кадра ↔ биты ↔ отсчёты звука).

```
┌─────────────────────────────────────────────────────────────┐
│  ПРИЛОЖЕНИЕ         file_sender.py / file_receiver.py / веб  │
│                     выбор файла, настройки, отчёт, UI        │
├─────────────────────────────────────────────────────────────┤
│  КАДРОВЫЙ УРОВЕНЬ   protocol.py                              │
│                     кадр AM01: имя, размер, SHA-256,         │
│                     блоки 64 Б + CRC32                       │
├─────────────────────────────────────────────────────────────┤
│  ФИЗИЧЕСКИЙ УРОВЕНЬ phy.py                                   │
│                     FSK-модуляция/демодуляция, маркеры,      │
│                     синхронизация, согласование режима       │
├─────────────────────────────────────────────────────────────┤
│  ЗВУК               sounddevice (Python) / WebAudio (браузер)│
└─────────────────────────────────────────────────────────────┘
```

Веб-приложение `index.html` содержит **точную JS-копию** обоих уровней (кадр + PHY), включая SHA-256 и CRC32, поэтому форматы бит-в-бит совместимы с Python-версией (это проверяет `tests/test_webapp.js`).

## Карта модулей

| Модуль | Роль | Ключевые функции |
|---|---|---|
| `src/phy.py` | физический уровень | `build_transmission` (эфир с согласованием), `decode_auto` (авто-приём), `make_params`, `validate`, пресеты частот |
| `src/protocol.py` | кадрирование | `build_frame`, `parse_frame`, `bytes_to_bits` |
| `src/file_sender.py` | CLI-передатчик | аргументы `--mode --symbol-ms --preset --base --step --marker` |
| `src/file_receiver.py` | CLI-приёмник | запись → `decode_auto` → отчёт и сохранение в `received/` |
| `index.html` | веб-клиент | UI + JS-копия phy/protocol + спектроанализатор |

## Тракт передачи (TX)

```
файл/текст
   │  build_frame()                      protocol
   ▼
кадр AM01 (заголовок + блоки с CRC32)
   │  bytes_to_bits() → биты → символы   phy
   ▼
FSK-символы (тон = base + step·k)
   │  синтез синусоид с фейдами 5 мс
   ▼
эфир: [маркер][CFG в базовом режиме][маркер][маркер P][ДАННЫЕ в режиме P][маркер P]
   │
   ▼
🔊 динамик
```

## Тракт приёма (RX)

```
🎤 микрофон (48 кГц, браузер — с отключёнными шумодавами)
   │
   ▼
1. Поиск маркера ─ окно 50 мс, шаг 10 мс: энергия маркерной частоты
   │                должна доминировать ≥25 окон подряд
   ▼
2. Точная синхронизация ─ перебор сдвигов ±0.6 символа с шагом 1/20:
   │                       максимум «уверенности» классификации 16 символов
   ▼
3. Служебная посылка (CFG) ─ декодируется базовым режимом,
   │                          проверка сигнатуры "AC" + CRC32
   │                          └─ CRC не сошёлся → legacy-режим (базовые параметры)
   ▼
4. Следящий декодер данных ─ каждый символ оценивается в трёх положениях
   │                          окна (раньше/по сетке/позже), сетка сдвигается
   │                          за лучшим → компенсация дрейфа часов
   ▼
5. Сборка кадра ─ CRC32 каждого блока → список битых блоков,
   │               SHA-256 всего файла → финальный вердикт
   ▼
файл + отчёт («блоки 12/12, SHA-256 сошёлся»)
```

## Ключевые алгоритмы

### Детекция тона
Энергия частоты f в окне — скалярное произведение сигнала с sin/cos опорными колебаниями (одноточечный ДПФ, аналог фильтра Гёрцеля). Символ = частота с максимальной энергией. Центральная часть символа (без четверти с каждого края) исключает межсимвольные переходы.

### Согласование режима (см. PROTOCOL.md)
Проблема курицы и яйца — «чтобы узнать параметры, надо уже знать параметры» — решена неизменным **базовым режимом** (4-FSK, 100 мс, тона 1500–2700, маркер 3500 Гц), в котором всегда передаётся короткая CFG-посылка. Данные затем идут в любом объявленном режиме.

### Следящая синхронизация (early-late tracking)
Кварцы двух устройств всегда чуть расходятся (~0.01–0.3%). За 50 секунд жёсткая символьная сетка уезжает на половину символа, и хвост кадра превращается в кашу. Решение: на каждом символе декодер пробует окно чуть раньше / по сетке / чуть позже и сдвигает сетку туда, где победивший тон сильнее всего отрывается от конкурентов. Запас слежения ~5% на символ покрывает любой реальный дрейф. Проверяется тестом с растяжением записи на ±0.25%.

### Защита от гармоник
Валидатор параметров запрещает маркер ближе 300 Гц к тонам и предупреждает, если маркер попадает на 2-ю/3-ю/4-ю гармонику тона (дешёвые динамики искажают сигнал, и гармоника ловится как ложный маркер — найдено в реальном эфире).

## Почему два клиента

| | Python CLI | Веб (index.html) |
|---|---|---|
| установка | Python + pip | не нужна, открыл и работает |
| телефоны | нет | да (HTTPS/localhost) |
| автоматизация, отладка | удобно | — |
| зависимость от интернета | нет | только первая загрузка страницы |

Один формат эфира — любые комбинации «кто передаёт / кто принимает».
